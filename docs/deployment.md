# Развёртывание

## TLS и база данных

Сервер слушает HTTPS на порту 7443. Для локального демо можно экспортировать сертификат разработки .NET для `localhost`. Выполните команды в интерактивном PowerShell.

```powershell
New-Item -ItemType Directory -Path certs -Force | Out-Null
$env:LAN_GUARD_TLS_PASSWORD = [guid]::NewGuid().ToString('N')
dotnet dev-certs https --trust --export-path .\certs\localhost.pfx --password $env:LAN_GUARD_TLS_PASSWORD
```

Для LAN используйте PFX с закрытым ключом и цепочкой УЦ. В SAN должно быть DNS-имя сервера или IP, который вводят администраторы и агенты. Ограничьте доступ к PFX и дайте контейнерному пользователю с UID 1654 право чтения. На Linux для отдельной копии PFX можно назначить владельцем UID 1654 и выставить права `0400`. На Windows настройте доверие к УЦ в хранилище локального компьютера, чтобы сертификат принимала служба.

Установите переменные из [README](../README.ru.md), задайте адрес сетевого интерфейса сервера и пароль PostgreSQL. Сервис PostgreSQL доступен только во внутренней сети Compose. Для первого запуска используйте сгенерированный пароль, как в примере.

```powershell
$env:LAN_GUARD_DEMO = 'false'
$env:LAN_GUARD_BIND_IP = '<LAN IP сервера>'
$env:LAN_GUARD_DB_PASSWORD = [guid]::NewGuid().ToString('N')
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.postgres.yml up --build
```

Сохраняйте пароль PostgreSQL для последующих запусков с тем же томом. Пароль администратора читается при создании первой записи. Данные и ключи защиты сессий сохраняются в томах Compose. Для эксплуатации защищайте эти тома и резервные копии и передавайте переменные через защищённое хранилище окружения. Ограничьте входящий порт управляемой сетью средствами сервера.

## Локальная сборка панели и API

```powershell
npm.cmd ci --prefix src/LanGuard.Web
npm.cmd run build --prefix src/LanGuard.Web
New-Item -ItemType Directory -Path src/LanGuard.Server/wwwroot -Force | Out-Null
Copy-Item src/LanGuard.Web/dist/* src/LanGuard.Server/wwwroot -Recurse -Force
$env:ASPNETCORE_URLS = 'https://localhost:7443'
$env:LanGuard__Demo = 'true'
$env:LanGuard__AdminPassword = '<ваш пароль из 16–256 символов>'
dotnet dev-certs https --trust
dotnet run --project src/LanGuard.Server
```

По умолчанию SQLite БД и ключи сессий создаются в `data/` относительно рабочего каталога процесса. Переменная `LanGuard__DataPath` задаёт другой каталог. Миграции применяются при старте сервера. Каталог правил можно заменить через `LanGuard__SignaturesPath` и перезапустить сервер. Новая версия правил применяется к следующим отчётам.

## Windows-агент

Служба использует LocalSystem для чтения системных источников. Установщик копирует файлы в `%ProgramFiles%\LanGuard`, сохраняет конфигурацию, защищённую DPAPI идентичность и очередь в `%ProgramData%\LanGuard`. Доступ к обоим каталогам есть у SYSTEM и локальных администраторов. Токен находится в защищённом ACL файле до завершения регистрации, затем агент удаляет файл.

Расписание по умолчанию составляет 30 секунд между heartbeat и 12 часов между полными проверками. Для изменения расписания администратор редактирует `%ProgramData%\LanGuard\agent.json` и перезапускает службу. При первом старте агент проводит инвентаризацию сразу. Режим `--inventory-only` печатает только покрытие источников и подходит для проверки доступа на стенде.

[Службы Windows в .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service)

Удаление регистрации службы выполняется в повышенном PowerShell. При необходимости сохраните данные и журналы для диагностики.

```powershell
Stop-Service LanGuardAgent
sc.exe delete LanGuardAgent
```

## Границы первой версии

Агент выполняет только исходящие HTTPS-запросы к указанному серверу и проверяет сертификат по системному хранилищу. Идентификатор машины привязан к случайному 256-битному секрету с ротацией. Сервер хранит хеши секретов и токенов, панель использует отдельную cookie-сессию с CSRF-защитой. Поддерживается один начальный администратор. Управление пользователями, отзыв агента через интерфейс, регламент автоматической очистки и уведомления об офлайне запланированы на следующие этапы.

Каталог использует имена и метаданные. Для бинарников издатель берётся из метаданных PE, для записей установки из реестра. Эти данные можно изменить. Средняя уверенность означает сочетание признаков, криптографическая подлинность требует проверки Authenticode. Стороннее ПО и компоненты Windows имеют отдельные категории. Обнаружение компонента RDP или WinRM само по себе отражает наличие компонента, а состояние включения функции требует отдельной проверки.

Для пользовательских источников агент проверяет только загруженные профили. Автозапуск ограничен ключами Run и RunOnce. В планировщике агент учитывает пути действий запуска EXE. Аргументы команд, содержимое скриптов и полное сканирование дисков в эту версию не входят. [API планировщика Windows](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskservice)
